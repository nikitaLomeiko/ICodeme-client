# Исправления авторизации ICodeme

Дата: 1 ноября 2026 года. Область: найденные в предыдущей проверке проблемы JWT, регистрации, восстановления пароля, OAuth, клиентских сессий и доступа к IDE.

Статус: исправления внесены в ICodeme-client и ICodeme-server. Серверный патч применён после проверки исходных хешей; резервная копия прежних серверных файлов находится в `/tmp/icodeme-auth-security-backup`. `.env` и секреты не изменялись.

## Что исправлено

| Проблема | Исправление |
| --- | --- |
| MongoDB-оператор вместо refresh-токена позволял выбрать чужую сессию | `/auth/refresh` читает только HttpOnly-cookie. TokenHelper проверяет строку и формат до обращения к БД; в запрос попадает SHA-256 токена. Остальные поля публичных auth-методов проверяются во время исполнения. |
| Telegram выдавал токены без проверки подписи | Оба Telegram-метода проверяют HMAC-SHA256. `auth_date` включён в подписываемые данные; сравнение подписи выполняется через `timingSafeEqual`. Отклоняются неверные типы, изменённые данные, недопустимые даты и данные старше 5 минут; допуск часов в будущее — 30 секунд. |
| Пароль менялся по одному userId | После подтверждения кода сброса выдаётся случайное одноразовое разрешение на 10 минут. В БД хранится его хеш; изменение пароля атомарно проверяет и погашает разрешение. Флаг `isResetPassword` больше не служит доказательством права на смену пароля. |
| После смены пароля старые токены продолжали работать | Меняется версия авторизации пользователя и удаляются все его refresh-сессии. JWT-guard проверяет пользователя, версию, существование и срок сессии при каждом защищённом запросе. |
| Коды подтверждения не имели срока и ограничения попыток | Срок — 10 минут, максимум 5 попыток на код; попытка резервируется атомарно. Подтверждение почты и сброс пароля имеют разные назначения. Код погашается однократно. Добавлены общие для процессов лимиты запросов в MongoDB по адресу и аккаунту. |
| IDE была доступна без авторизации и проверки владельца | Включены JWT-guards на Docker/project-контроллерах. userId берётся из авторизованной сессии. Перед отправкой ввода, остановкой, удалением и заменой контейнера проверяется метка владельца. Имена контейнеров разделены по пользователям. Также проверяются пути и ограничения дерева файлов. |
| Один refresh-токен обновлялся несколько раз одновременно | Замена хеша выполняется атомарным сравнением и обновлением. Только один запрос может успешно использовать старый токен. Обычный вход больше не удаляет сессии других устройств. |
| Ответ приходил раньше сохранения сессии | Выдача и обновление токенов ожидают завершения записи в БД. |
| Старый запрос обновления завершал или перезаписывал новый вход | Клиент отслеживает поколение сессии и отбрасывает устаревшие ответы. Операции входа, выхода и обновления сериализованы; между вкладками используется Web Locks. Перед обновлением повторно проверяется актуальная cookie-сессия. |
| Любой 401 запускал refresh, включая неверный пароль | Автоматическое обновление применяется только к защищённым запросам. Ошибка входа остаётся ошибкой входа. Сетевой сбой, 429 и 5xx не удаляют сессию и не вызывают принудительный переход на `/auth`. |
| Logout оставлял неопределённое состояние и вечный loader | После истечения сессии `isAuthenticated=false`. При недоступном сервере во время начальной проверки показывается повторная попытка. Доверия к данным localStorage больше нет. |
| Токены попадали в localStorage, URL, логи и БД открытым текстом | Access и refresh находятся в HttpOnly-cookie, в production — Secure. OAuth возвращает на чистый `/oauth/success`. В HTTP-ответах входа нет токенов; отладочные логи с секретами удалены. В БД сохраняется только хеш refresh. Старый `auth_token` удаляется без JSON.parse. |
| Не было серверного выхода | Добавлен `/auth/logout`, который отзывает текущую сессию и очищает cookie. Кнопка выхода находится в настройках и сообщает об ошибке, если сервер недоступен. |
| OAuth не проверял связь callback с начатым входом | Для Google/GitHub добавлен случайный `state`, связанный с HttpOnly-cookie на 10 минут. Google использует проверенный email и настоящий provider id; предусмотрен переход со старого формата googleId. GitHub сверяет provider id существующего аккаунта. |
| После перехода на cookie возникал риск CSRF | Изменяющие запросы требуют Origin из явного списка разрешённых адресов; тот же список используется CORS. Cookie по умолчанию SameSite=Lax. |
| Любая ошибка профиля отправляла на создание профиля | На `/auth/profile` ведёт только 404. При наличии профиля вход ведёт на `/profile`; другие ошибки отображаются с повторной попыткой. Это применяется к обычному входу, регистрации и OAuth. |
| Кэш предыдущего аккаунта мог остаться после смены пользователя | На границах аккаунта сбрасываются кэши auth/profile/study/document/ide. Другие вкладки получают уведомление о смене сессии и перезагружают состояние. |
| Проверки авторизации повторялись из-за вложенных layout | Удалены повторные RootLayout и провайдеры из групп маршрутов. На личных страницах включены существующие withAuth/withAccount. |
| Telegram возвращал на другой hostname | Кнопка Telegram формирует origin и return_to из текущего адреса приложения; больше нет принудительного перехода с localhost на 127.0.0.1. |
| Известный запасной JWT-секрет | Запуск с отсутствующим или коротким JWT_SECRET запрещён. Минимум — 32 символа. Текущее значение проверено по длине и не изменялось; секреты в отчёт не включены. |

Дополнительно исправлено поле последнего шага настройки профиля: проверяется `info`, соответствующее схеме формы, вместо отсутствующего `language`. Существующие изменения регистрации и HTML-шаблон письма сохранены.

## Сроки и поведение сессии

- Access JWT: **15 минут** вместо 30 секунд. При просрочке клиент обновляет сессию и повторяет исходный запрос.
- Refresh-сессия: **30 дней от входа**, без продления общего срока при обновлении. Cookie может сохраняться дольше последнего серверного срока, но сервер всегда проверяет абсолютный срок записи.
- Если refresh истёк, отозван или невалиден, защищённые страницы требуют повторного входа.
- Если сервер временно недоступен, сессия не сбрасывается только из-за этой ошибки.
- Неверный пароль не запускает refresh и не выдаёт новую сессию.
- Выход отзывает текущую сессию; смена пароля — все сессии аккаунта.
- Старые JWT и refresh-записи прежнего формата не принимаются. После обновления потребуется войти заново. Старые коды подтверждения нужно запросить повторно.

## Настройки запуска

Клиент и сервер нужно обновить совместно: контракт передачи токенов изменён.

| Параметр | Значение / назначение |
| --- | --- |
| Сервер `JWT_SECRET` | Случайный секрет минимум 32 символа; существующий настроен. |
| Сервер `FRONTEND_ORIGINS` | Разрешённые Origin через запятую, например `http://localhost:5173`. Если не указан, используется `FRONTEND_URL`, затем локальные значения по умолчанию. |
| Сервер `FRONTEND_URL` | Адрес возврата OAuth, локально `http://localhost:5173`. |
| Клиент `NEXT_PUBLIC_BACKEND_URL` | Адрес API с завершающим `/`, локально `http://localhost:3000/`. |
| Клиент `NEXT_PUBLIC_TELEGRAM_BOT_ID` | ID Telegram-бота; сохранено прежнее значение по умолчанию. Домен возврата должен быть разрешён в настройках бота. |
| Клиент `NEXT_PUBLIC_TELEGRAM_ORIGIN` | Telegram `origin` и `return_to`; локальное значение по умолчанию `http://127.0.0.1:5173`, совпадает с исходной ссылкой бота. |
| Сервер `NODE_ENV=production` | Включает Secure-cookie; требуется HTTPS. |
| Сервер `AUTH_COOKIE_SAME_SITE=none` | Только при необходимости разных сайтов frontend/backend, с production HTTPS. Предпочтительно размещение в пределах одного сайта. |
| Сервер `TRUSTED_PROXIES` | При работе через reverse proxy — доверенные IP/CIDR через запятую. По умолчанию заголовкам клиента об IP не доверяем. |

Не смешивать `localhost` и `127.0.0.1` в одной сессии. Адреса Google/GitHub callback должны соответствовать настройкам провайдеров и hostname API. В локальном режиме сервер разрешает пару `localhost`/`127.0.0.1`, когда задан только один loopback адрес. Если задан `FRONTEND_ORIGINS`, перечислите там точный origin фронтенда. Для ручных изменяющих запросов к API нужен разрешённый заголовок `Origin`. Развёртывание требует HTTPS, если frontend/backend находятся на разных сайтах.

При подключении MongoDB создаются TTL-индексы для refresh-сессий, кодов и записей ограничения запросов. У DB-пользователя должны быть права на создание индексов. Истечение срока проверяется в коде независимо от задержки TTL-очистки.

## Проверки

- Сервер: `npm run build` — успешно в подготовленной копии.
- Сервер: `TS_NODE_TRANSPILE_ONLY=true node -r ts-node/register -r tsconfig-paths/register test/auth-security.test.cjs` — **14 проверок успешно**, включая повторный запуск после применения в ICodeme-server.
- Сервер: `tsc --noEmit --incremental false` — успешно после применения.
- Клиент: `npx tsc --noEmit --incremental false` — успешно.
- Клиент: `node tests/auth-security.test.cjs` — **8 проверок успешно**.
- ESLint изменённых TS/TSX-файлов — без ошибок. Остались два предупреждения React Compiler о `watch()` из React Hook Form в существующих формах.

Серверные проверки покрывают подпись и срок JWT, отказ при слабом секрете, NoSQL-инъекцию, хранение хеша, независимость сессий, атомарность ротации и повторное использование, ожидание записи, Telegram, одноразовый сброс, версии сессий, cookie/Origin/OAuth state, доступ к Docker и лимиты запросов. Клиентские — одновременные 401, неверный пароль, отказ сервера, истёкший refresh, устаревшие ответы, logout и уведомления вкладок без перезагрузки отправителя.

Это регрессионные проверки реальных модулей с подменёнными HTTP/DB/Docker-зависимостями. Живые входы у OAuth-провайдеров, доставка почты, работа на реальной MongoDB и запуск контейнеров здесь не выполнялись. Межвкладочная блокировка требует Web Locks; без него остаётся очередь внутри одной вкладки. Проверка не является полным аудитом безопасности всего приложения или изоляции исполнения пользовательского кода.
